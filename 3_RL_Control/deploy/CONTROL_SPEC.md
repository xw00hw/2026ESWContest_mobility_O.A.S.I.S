# 볼스터 제어 사양

> Raspberry Pi 런타임(`oasis_rt.app`)이 쓰는 관측·행동·예측기·튜닝 규칙·SAC 잔차 정책(v8)·실물 G 제어와 체형 스케일(v9)·안전 계층·세션 규칙을 한 곳에 정리한 사양서입니다.
> 대상 구성은 Raspberry Pi 5 + BeamNG.drive(Collector 입력) + STM32 펌웨어 OASIS_FALLBACK v2입니다.

## 0. 제어기 구성

Pi에서는 아래 세 제어기 중 하나가 동작합니다. 주행 입력, 보드 링크, 안전 계층은 셋이 같습니다.

| | **RL 정책 (기본)** | **튜닝 규칙 (hot fallback)** | **FB V6 (cold fallback)** |
|---|---|---|---|
| 내용 | 튜닝 규칙 + SAC 잔차 신경망 | 규칙만 (RL의 prior) | 백업 제어기 `4_Seat_Actuation/experiment_a`를 그대로 import (V6 제어 법칙 + 큰 a_y 포화 + 충격 OFF) |

| 학습 / 튜닝 | 시뮬레이터 v8(보드 구동기 모델), 규칙에서 출발해 ±0.25 보정, 보상 = 평가 점수, 200k 스텝 × 4 시드 | 같은 시뮬레이터, 72개 격자 탐색 | 백업 제어기 설계값, STM 튜닝값 사용 |

## 2. 출력: 행동 → 볼스터 목표각

행동은 `a = [c, d]`, 각 성분은 [−1, 1]입니다. RL 정책과 튜닝 규칙이 같은 변환(`obs_layout.action_to_targets`)을 씁니다.

```text
c' = (c + 1)/2 · θmax/2          d' = d · θmax/2          θmax = 20°
yaw_L = clip(c' + d', 0, 20°)     yaw_R = clip(c' − d', 0, 20°)     pitch_L = pitch_R = 0   (yaw 전용 모델)
```

- c = −1, d = 0이면 양쪽이 열립니다(0°).
- d < 0이면 오른쪽이 조입니다. 왼쪽으로 돌 때(a_y > 0) 몸이 오른쪽으로 밀리므로 그쪽을 받칩니다.

## 3. a_y 미리보기: 1초 예측기

구현: `oasis_rt/predictor.py`의 `BeamNGPredictor`. 학습(시뮬레이터)과 Pi가 같은 클래스와 같은 가중치 파일(`model_v8/predictor.npz`)을 씁니다. 구동기 상태는 미리보기에 들어가지 않습니다.

BeamNG.drive + Collector 구성에는 **앞 도로 정보와 요레이트가 없습니다.** 예측기는 이 조건(`road_valid` = 0, 요레이트 = a_y / max(v, 5))으로 학습했습니다.

| 입력 (31개, 20 Hz) | 출처 |
|---|---|
| 핸들 사전 예측 a_y(h) 10개 | `WheelPreviewPredictor`: 핸들 각 + 조향 속도 외삽(Ts 0.3 s) → 정상상태 a_y → 요 지연 0.12 s. 공칭 차량(휠베이스 2.7 m, 조향비 15) |
| 앞 도로 a_y(h) = v² κ(s + v h) / g 10개 + 유효 플래그 | 도로 정보가 있는 브리지(BeamNG.tech) 전용 입력. 이 구성에서는 항상 0 (학습도 0) |
| 현재 a_y, a_x, 요레이트, 속도, 핸들 각·속도, 0.1–0.4 s 전 a_y | Collector 행 (요레이트는 a_y / max(v, 5) 추정, 시뮬레이터도 같은 식) |

- 출력은 **핸들 사전 예측 + MLP 잔차**(31 → 64 → 64 → 10)입니다. 가중치가 없으면 핸들 사전 예측과 같습니다.
- 학습 데이터: 시뮬레이터 v8 1,200 에피소드(93만 스텝, 시드 20000+), 검증 240 에피소드(18.7만 스텝, 시드 21000+). 행 주기 25–60 Hz(Collector).

**검증 RMS [g]** (`results/v8/predictor_eval.json`, 도로 정보 없음)

| 예측 시간 | 0.1 s | 0.3 s | 0.5 s | 0.7 s | 1.0 s |
|---|---|---|---|---|---|
| **예측기 (배포)** | 0.023 | 0.038 | 0.054 | 0.070 | **0.090** |
| 핸들 사전 예측만 | 0.033 | 0.056 | 0.078 | 0.101 | 0.134 |
| 미리보기 없음 (현재 값 유지) | 0.034 | 0.063 | 0.088 | 0.112 | 0.140 |
| 참고: 도로 정보가 있는 경우 (BeamNG.tech) | 0.023 | 0.035 | 0.046 | 0.056 | 0.069 |

- 1초 앞 오차는 현재 값 유지의 64 %입니다. 도로 정보가 있으면 0.069 g까지 내려가지만 이 구성에서는 쓸 수 없습니다.
- 기동별 1초 오차 (예측기 / 현재 값 유지): 차선 변경 0.104 / 0.185, 슬라럼 0.100 / 0.217, 도심 회전 0.127 / 0.147, 무작위 조향 0.091 / 0.096.
  - 예측 근거가 없는 무작위 조향에서는 현재 값 유지와 같습니다. 억지로 예측하지 않습니다.

**한계**
- 차선 변경과 슬라럼의 이득에는 합성 기동 모양을 배운 몫이 섞여 있습니다. 실제 BeamNG 주행 로그(Collector 원본)로 다시 검증해야 합니다.
- 요레이트 추정(a_y / v)은 정상 원선회에서만 정확합니다. 시뮬레이터도 같은 추정을 쓰므로 학습과 배포의 입력은 같지만, 과도 구간에서 실제 요레이트와의 차이는 실제 로그로 확인해야 합니다.

## 4. 튜닝 규칙

RL 정책의 prior이자 hot fallback입니다.

```text
ay = ay_pred[0.7 s]                          관측 6번 = 예측기의 0.7초 앞 값
m  = max(|ay| − deadband, 0)                 deadband = 0
c  = −1                                      공통 조임 없음
d  = clip(−gain · sign(ay) · m, −1, 1)       gain = 16 /g
```

- 각도로 풀면 **밀릴 쪽 볼스터 = min(10°, 160°/g × |a_y(0.7 s)|)**, 반대쪽은 0°입니다.
- 0.063 g에서 10°에 도달합니다. 보드 구동기가 yaw 약 5–6 °/s로 느리기 때문에, 목표가 빨리 커지는 높은 gain이 유리합니다.

### 튜닝 절차 (`sim/v3/tune_rule.py --grid`, 결과 `results/v8/rule.json`)

- 격자: gain {6, 8, 10, 12, 14, 16} × 미리보기 {0.3, 0.4, 0.5, 0.7, 0.9, 1.0 s} × deadband {0, 0.02 g} = 72개.
  - 구동기가 느리므로 미리보기 범위를 1.0 s까지 넓혔습니다.
  - 채택된 gain 16은 격자 끝입니다. 이보다 높으면 사실상 on/off 동작이 되므로 더 넓히지 않았습니다.
- 에피소드 점수 (높을수록 좋음):
  - CoM RMS 감소율 [%]
  - − 0.5 × "볼스터가 더한 압박 > 20 N"인 시간 [%]
  - − 100 × 평균((추가 압박 − 20)/20)²
- J는 튜닝 에피소드 48개(시드 2000+, 레벨 1·2)에 대한 10 % 절사평균입니다.
- 튜닝 상위 5개를 **검증 에피소드 48개(시드 3000+)** 로 다시 채점해, 검증 J가 가장 높은 후보를 골랐습니다. 튜닝 시드에 대한 과적합을 피하기 위해서입니다.

| 후보 | 튜닝 J | 검증 J | 검증 CoM 감소 | 20 N 초과 시간 |
|---|---|---|---|---|
| **gain 16, 0.7 s (채택)** | 4.47 | **5.38** | 10.3 % | 6.7 % |
| gain 16, 0.9 s | 4.29 | 5.37 | 10.3 % | 6.7 % |
| gain 14, 0.7 s | 4.35 | 5.31 | 10.1 % | 6.5 % |
| gain 14, 0.9 s | 4.18 | 5.26 | 10.0 % | 6.4 % |
| gain 16, 1.0 s | 4.20 | 5.21 | 10.1 % | 6.8 % |
| 참고: gain 8, 0.7 s | 3.80 | 5.21 | 8.7 % | 5.1 % |

- 상위 후보 간 검증 J 차이(0.2 이내)는 작습니다. gain 14–16, 미리보기 0.7–0.9 s 범위면 성능이 비슷합니다.

## 4b. 실물 G 제어와 체형 스케일 (v9)

구현: `oasis_rt/g_residual_control.py`, `oasis_rt/body_scale.py`.

실물 착석 시험의 제어기는 **측정 횡가속도(G) 기반 기본 곡선 + v8 정책의 제한된 보정**입니다. 실행 설정은 [`experiments/seated_trial/`](experiments/seated_trial/README.md)의 시험 프로파일이 켭니다(`config.yaml`의 기본값은 `g_residual_control.enabled: false`). v9는 이 구조를 그대로 두고 **체형 스케일 s 하나만** 더합니다.

```text
기본각   base(|G|) = 0.01 g 0° → 0.0625 g 10° → 1 g 20° (구간 선형)      예측만: 최대 10°, 100 ms 확인
v9       base' = min(s · base, 20°),  preview' = min(s · preview, 10°)     s: 세션마다 한 번 정해 고정
보정     ±1.5° (정책 각 − 학습 prior 각), 1 g에서 0°로 축소
s        = clip(1 + K_W (r_w − 1) + K_T (r_t − 1), 0.9, 1.1)               K_W = −1.2, K_T = 0 (앉은키는 기록만)
r_w      = (어깨폭 px / 화면 폭) / 0.2665          r_t = (어깨→골반 높이 px / 화면 높이) / 0.424
```

### 기준 사용자와 비율 측정

- **기준 사용자**는 실물 착석 시험의 착석자입니다. 이 사람에게 현재 설정이 잘 맞는 것을 확인했으므로 s = 1로 둡니다.
  - 기준값은 시험 세션의 Pi RTMPose 뷰어 녹화(저장소 미포함)에서 쟀습니다. 0–61 s 구간 294프레임의 오버레이에서 어깨·골반 점을 읽었습니다(`sim/v3/reference_body_from_video.py`, `results/v9/reference_user.json`).
  - 결과: 어깨폭 0.2665(화면 폭 대비, 변동계수 2.8 %), 어깨→골반 높이 0.424(화면 높이 대비, 변동계수 3.6 %). 62 s 이후는 영상 디코딩 손상으로 제외했습니다.
- **다른 착석자**는 세션 전에 수집한 카메라 중립 파일(`oasis.rtmpose.neutral.v1`, 작업자 확인)로 r을 계산합니다(`body_scale.neutral`). 주행 중 프레임으로 다시 계산하지 않습니다.
  - 화면 대비 비율이므로 해상도와는 무관합니다. 단, 카메라 위치·렌즈·모드·좌석 위치는 기준 측정 때와 같아야 합니다.
  - r이 0.7–1.4를 벗어나면 구도가 바뀐 것으로 보고 시작을 거부합니다.
- **바뀌지 않는 것:** 방향 선택, 예측 확인 시간, RL 보정 폭, 필터(τ 0.3 s), 속도 게이트, 압력 해제(2500 count), CAD·STM·IK 투영, 정책 관측의 체형값(`profile.from_camera: false`).
- `body_scale.enabled: false`(기본)이면 s = 1이고 실물 시험 제어기와 출력이 같습니다. 이 동등성은 단위 시험으로 고정했습니다.

### 튜닝 (`sim/v3/tune_body_scale.py`, `results/v9/body_scale.json`)

- 시뮬레이터 v8에서 Pi와 같은 G 제어기 코드를 그대로 import해 실행했습니다.
  - v8 정책은 배포 profile(75 kg / 0.42 m / 0.58 m)을 봅니다.
  - 보드 설정은 실물 시험과 같습니다(STM yaw 10 °/s, 상한 20°).
- 체형 9개(어깨폭 0.36–0.48 m, 앉은키 0.50–0.66 m) × s 9개(0.8–1.2)를 같은 48 에피소드(시드 3000+, 레벨 1·2)로 비교했습니다.
- **선택 기준은 지지량(평균 CoM RMS 감소)입니다.**
  - 기준 체형(0.42 / 0.58)의 최적은 s = 0.997로, 기준 착석자의 주관 평가(현재 설정이 가장 적합)와 일치합니다.
  - 압박 벌점이 포함된 평가 점수로는 기준 체형도 s = 0.8(격자 끝)을 고릅니다. 실제 체감과 반대이므로 진단용으로만 기록했습니다.

| 체형 (어깨폭 / 앉은키 m) | 지지 최적 s [90 % 구간] | 원인 (시뮬레이터) |
|---|---|---|
| 0.36 / 0.58 | ≥ 1.2 [0.92, 1.2] | 몸과 볼스터 사이 틈 → 더 닫아야 닿음 |
| 0.39 / 0.58 | ≥ 1.2 [0.83, 1.2] | 〃 |
| **0.42 / 0.58 (기준)** | **0.997** | — |
| 0.45 / 0.58 | 0.904 | 예압이 커서 일찍 닿음 |
| 0.48 / 0.58 | 0.848 | 〃 |
| 0.42 / 0.50, 0.54 | 0.973, 0.966 | 상·하 패드 분담 |
| 0.42 / 0.62, 0.66 | 1.020, ≥ 1.2 | 〃 (구간이 넓어 근거 약함) |

## 5. RL 정책 (SAC 잔차)

### 5.0 알고리즘 선택

문제의 특징:
- 행동이 연속 2차원입니다.
- 관측이 부분적입니다. 인체 상태를 직접 볼 수 없어 9프레임 이력을 씁니다.
- 시뮬레이터에는 특권 정보가 있습니다(CoM, 접촉력, 파라미터).
- 보상은 쌍둥이(볼스터를 연 같은 사람) 대비라서 잡음이 큽니다.
- 시뮬레이터가 느립니다. 코어당 약 55 스텝/s, 에피소드 40 s.
- 배포 대상은 결정적 MLP 하나이고, 규칙 위의 잔차입니다.

| 후보 | 장점 | 이 문제에서의 단점 | 판단 |
|---|---|---|---|
| **SAC** | off-policy라 표본 효율이 높음. 엔트로피 탐색이 잡음 많은 도메인 랜덤화(DR)에 강건. 평균 행동이 결정적이라 잔차·배포가 단순 | α 조정, Q 과대추정 (클립·α 상한으로 처리) | **채택** |
| TD3 | 결정적, 안정적 | 탐색 잡음을 수동으로 정해야 함. 확률적 보상에 덜 강건 | 이점 없음 |
| PPO | 안정적, 병렬화 쉬움 | on-policy라 표본이 10–50배 필요. 200k 스텝 예산으로는 부족 | 제외 |
| TQC / DroQ (SAC 변형) | 과대추정 감소, 표본 효율 | 구현 복잡도 대비 이득이 점진적 | 향후 후보 |
| 모델 기반 / MPC | 물리 모델 활용 | 인체 모델 불확실성이 크고 Pi 연산 부담 | 제외 |

구조 요소:
- 비대칭 critic (특권 상태 31개 추가)
- 튜닝 규칙 위의 잔차
- CAPS 매끄러움 정규화
- 이력 K = 8
- 보상 스케일 20, α ≤ 1, 그라디언트 클립 10

```text
a = clip( rule(o) + 0.25 · tanh(μθ(x)), −1, 1 )    x = 정규화된 관측 이력 9 × 57 = 513 (±5 클립)
μθ : 513 → 256 → 256 → 2, ReLU                    결정적 실행 (평균 행동)
```

- 신경망 출력이 0이면 정확히 튜닝 규칙이 됩니다. 신경망이 바꿀 수 있는 폭은 ±0.25(행동 단위, yaw 약 ±2.5°)입니다.

### 5.1 설계 근거: 보상을 평가 점수와 같게 맞춘 이유

이전 설계의 보상(절대 CoM² 기반, 아래 "이전 보상")으로 같은 환경에서 학습한 정책(`v8a_s0`, `v8a_s1`)은 평가 점수가 튜닝 규칙보다 낮았습니다(같은 에피소드 차 −7.1, −5.5). 보상을 항별로 나누면 원인이 드러납니다(`sim/v3/reward_diag.py`, `results/v8/reward_diag.json`, 평가 은행 48 에피소드 평균).

| 이전 보상 기준 | CoM 이득 | 출력 변화 | 추가 압박 | 과압박 | **보상 합** | **평가 점수** |
|---|---|---|---|---|---|---|
| 볼스터 열림 (passive) | 0 | −0.3 | 0 | 0 | **−0.3** | **0** |
| 튜닝 규칙 | +15.4 | −8.4 | −8.3 | −20.0 | **−21.8** | **+4.7** |
| `v8a_s0` | +14.6 | −6.7 | −8.3 | −11.2 | −12.2 | −2.4 |
| `v8a_s1` | +13.7 | −6.4 | −7.3 | −16.9 | −17.3 | −0.8 |

- **보상과 평가 기준이 서로 다른 제어기를 좋다고 판단했습니다.**
  - 이전 보상으로는 튜닝 규칙이 아무것도 안 하는 것보다 나쁩니다(−21.8 vs −0.3). 비용이 CoM 이득의 2.4배입니다.
  - 평가 점수로는 규칙이 낫습니다(+4.7). 규칙과 passive의 우열이 두 기준에서 일치한 에피소드는 35 %뿐이었습니다.
- **RL은 자기 보상은 잘 올렸지만**(규칙 대비 +9.6, +4.5), 그 방향이 "덜 움직이기"라서 평가 점수가 떨어졌습니다.
- **CoM 항의 가중이 달랐습니다.**
  - 이전 보상은 절대 CoM²(2 cm 단위)라서 크게 흔들리는 소수 에피소드가 지배합니다.
  - 평가는 에피소드마다의 상대 감소율이라 모든 에피소드가 같은 무게입니다.
  - 그래서 절대 CoM 이득은 거의 지키면서(15.4 → 14.6) 평균 감소율은 크게 잃었습니다(10.3 → 2.4 %).
- **데이터 한계도 겹칩니다.**
  - 볼스터가 줄이는 몸의 움직임 자체가 작습니다. 볼스터를 연 채의 CoM RMS 중앙값이 0.59 cm이고, 규칙은 이를 약 10 %(약 0.6 mm) 줄입니다.
  - 볼스터 → 몸 권한은 직접 측정값이 아니라 실차 1회(동승자)와 벤치 2명의 압력 비로 간접 추정한 값입니다([`PARAMS_FINAL.md`](../sim/v3/final/PARAMS_FINAL.md)).
  - 구동기가 느립니다(yaw 약 5–6 °/s). 좋은 미리보기를 가진 규칙이 이미 제어 가능한 범위의 대부분을 씁니다.
  - 따라서 RL이 규칙과 전혀 다른 제어를 찾기보다 **규칙에서 출발해 조금씩 보정하는 구조**를 택했습니다.

### 5.2 학습 설정

**보상 = 평가 점수** (`sim/v3/overlays/reward_score.yaml`, `env_v3` `reward.mode: score`). 스텝마다 아래 값을 더하면 에피소드 점수가 됩니다.

```text
r = 50 (y_twin² − y²) / Σ_에피소드 y_twin²                       → CoM RMS 감소율 [%] (1차 근사)
    − (50 · [ΔF > 20 N] + 100 · ((ΔF − 20)/20)²₊) / 스텝 수      → −0.5 × 20 N 초과 시간 [%] − 100 × 과압박²
    − 0.01 Σ Δa²  − trip                                          → 작은 매끄러움 항 (규칙의 떨림 ≈ 0.3점)
```

- y는 상체 CoM 횡변위(÷ 2 cm), y_twin은 같은 사람을 볼스터를 연 채로 둔 쌍둥이입니다. 쌍둥이는 정책과 무관하므로 에피소드 시작 때 한 번 미리 돌려 분모(Σ y_twin²)를 구합니다(바닥값 1 mm RMS).
- ΔF는 쌍둥이 대비 볼스터가 더한 압박입니다.
- 볼스터를 연 채로 두면 보상은 정확히 0(첫 스텝 −0.01)입니다. 이 보상은 검증 에피소드에서 규칙을 passive보다 높게 평가합니다(시뮬레이터 감사 10번, 순서 일치 88 %).

**규칙에서 출발하는 SAC** (`sim/rl/sac_asym.py`, 실행 `v8_s0`–`v8_s3`, prior = §4 규칙)

| 항목 | 설정 |
|---|---|
| critic 선학습 | 처음 20k 스텝은 critic만 학습, 정책은 규칙 + 작은 탐색 잡음 (`--actor_delay 20000`) |
| 초기화 | 출력 층 0 (신경망 출력 0 = 규칙), 탐색 표준편차 e⁻¹ (`--init_log_std −1`), 워밍업 잡음 0.1 |
| 보정 크기 벌점 | 0.02 · \|tanh μ\|² (`--res_l2`) — 근거가 약한 곳에서는 규칙에 머무름 |

| 주기 · 할인 · 길이 | 20 Hz, γ 0.98, 200k 스텝 |
| 커리큘럼 | 난이도 레벨 0 → 2 (학습의 60 %까지) |
| CAPS | 시간 2.0, 공간 0.5 |
| 하드웨어 | 4 시드 GPU 동시 학습(`--device auto`, RTX 4070 SUPER, 시드당 약 19 ms/스텝, 약 1시간). 신경망이 작아 GPU는 한 시드 가속보다 여러 시드 동시 실행에 유리 (CPU 2 시드 16 ms/스텝) |

**도메인 랜덤화** (범위와 근거는 [`PARAMS_FINAL.md`](../sim/v3/final/PARAMS_FINAL.md))

| 대상 | 내용 |

| **`v8_s1` (선택)** | **5.93** | +0.64 | 31 / 48 | 3.92 |
| `v8_s3` | 5.84 | −0.88 | 23 / 48 | 3.76 |
| `v8_s2` | 5.78 | −0.12 | 27 / 48 | 2.29 |
| `v8_s0` | 5.74 | +0.75 | 26 / 48 | 2.97 |

### 해석

- **RL `v8_s1`은 튜닝 규칙과 같은 수준입니다.**
  - J 3.92 vs 3.93, 중앙값 차 +0.02, 48개 중 32개에서 우세, Wilcoxon p = 0.28.
  - 평균 차 −0.95는 대부분 에피소드 하나(1015 L0, 실차 재생, 동승자: 11.3 vs 50.7)에서 나옵니다. 이를 빼면 평균 차는 −0.13입니다.
  - 규칙보다 분명히 낫다고 할 근거는 없습니다. RL은 여러 에피소드에서 작게 이기고, 가끔 크게 집니다.
- **보상 정렬로 "RL이 자기 fallback보다 나쁜" 문제를 없앴습니다.**
  - 같은 구동기에서 이전 정책(−5.8)과 이전 보상 정책(−5.5, −7.1)은 규칙보다 분명히 나빴습니다.
  - 원인은 §5.1의 보상 불일치였고, 보상을 평가 점수로 바꾸고 규칙에서 출발하자 손실이 사라졌습니다.
  - 규칙보다 크게 나아지지 않는 것은 §5.1의 데이터 한계(줄일 흔들림이 작음, 권한 간접 추정, 느린 구동기)와 맞습니다.
- **시드 차이가 큽니다.**
  - 네 시드 모두 검증 J로는 규칙보다 높았지만, 평가 은행에서는 `s0`, `s2`가 꼬리 에피소드에서 크게 잃었습니다(p10 −9.3, −15.4; 규칙 −0.56).
  - 10 % 절사평균 J는 꼬리를 잘라 내므로 검증 J만으로는 이 위험이 보이지 않습니다.
  - `v8_s1`은 두 평가 모두에서 규칙 이상인 유일한 시드입니다. 선택 기준에 꼬리(p10)나 같은 에피소드 차의 평균을 넣는 것이 향후 개선점입니다.
- **압박:** RL의 20 N 초과 시간은 규칙과 비슷하거나 약간 적습니다(L2 6.9 vs 7.5 %). 최대 추가 압박은 L2에서 46 vs 42 N으로 큽니다.
- **FB V6(cold fallback)보다는 분명히 낫습니다.**
  - J는 규칙 3.93, FB V6 1.70입니다. FB V6이 규칙보다 나은 에피소드는 48개 중 10개입니다(Wilcoxon p < 0.001).
  - FB V6은 덜 누르지만(2–3 %) CoM도 덜 줄입니다(3.5–4.4 %).
- **배포:** `v8_s1`을 `control.mode: rl`로 두고 튜닝 규칙을 hot fallback으로 둡니다.
  - 시뮬레이터에서는 `control.mode: rule`도 같은 성능입니다. 벤치 주관 평가에서 RL의 체감이 규칙보다 나쁘면 `rule`을 권합니다.

## 8. 세션과 fallback

구현: `oasis_rt/app.py`.

```text
정책 준비 (모델·백엔드 검사)  ──실패──► control.cold_fallback: fb_v6 (null이면 시작 거부)
보드 handshake: HELLO v2(270°, 2 µs, lease 500) → FB_OFF → CAD(sha256) → TUNE(고정) → DISABLE → FSR HELLO → START_12,15 → STATE(OFF)
유효 주행 행 + PWM OFF 2 s 연속 ──► FB_ARM,<floor+1>,<tune rev> (한 번)
ARM 후 STATE가 중립(pose = target = 0)인지 0.5 s 안에 확인
rl / rule: 중립에서 압력 기준선 2 s (lease는 주행 입력이 유효할 때만 갱신)
제어: rl / rule 20 Hz, fb_v6 50 Hz;  PING 100 ms · STATE 100 ms · SET ≥ 40 ms · 압력 PING 1 s
입력·보드·정책 오류 → FB_OFF → DISABLE → STATE로 OFF 확인 → 종료 (자동 재ARM 없음)
```

| 상황 | 동작 |
|---|---|
| 정책 예외 / NaN / inf | 튜닝 규칙으로 전환, **세션 끝까지 유지 (latched)** |
| 시작 시 통과하는 정책 백엔드가 없음 | 처음부터 규칙 |
| 예측기 출력 NaN | 그 tick만 현재 a_y 유지 |
| 모델이 다른 구동기용 (manifest `actuator.mode` ≠ `fb_a2`) | 규칙으로 세션 (`control.actuator_mismatch: rule`; `run`이면 경고만) |
| STM `yaw_rate` < 학습 최소(10 °/s) 또는 `yaw_max` < 학습 최소(15°) | 규칙으로 세션 |
| 모델 패키지 없음 / 해시 불일치 | FB V6 (cold fallback) |
| ARM 전 입력 문제 | 2 s 검증을 처음부터 다시 (ARM하지 않음) |
| ARM 후 입력 문제 | OFF, 종료 |

- 규칙 파라미터는 모델 manifest의 prior(`ff_gain`, `ff_idx`)입니다. RL 학습의 기준 규칙과 같고, `results/v8/rule.json`의 best와도 같습니다.
- FB V6는 백업 제어기의 `Settings` 기본값 위에서 동작합니다. 튜닝값 여섯 개(yaw/pitch 상한·속도, 최대 반응 a_y, pitch 배율)는 STM이 확정한 값으로 바뀝니다(`tuning.apply_firmware_tuning`). 조향 선제 부호는 `beamng.steer_sign`을 따릅니다.

## 9. 설정

`deploy/runtime/config.yaml`의 주요 항목입니다.

```yaml
model_dir: ../model_v8
rig: static_bench                      # 정지 벤치: 인터락에서 관성하중을 빼지 않음
predictor: {kind: model}               # manifest의 예측기 (model_v8/predictor.npz)
control: {mode: rl, fallback: true, cold_fallback: fb_v6, actuator_mismatch: rule, rule: {}}
link: {firmware: fallback_v2, port: /dev/ttyACM0, baud: 460800}
beamng: {listen: [0.0.0.0, 64257], allow_from: [], fresh_ms: 200, max_pc_age_ms: 50, startup_s: 2.0, steer_sign: 1}
confirmations: {hardware_mapping_checked: false, neutral_start_clear: false, stm_tuning_reviewed: false,
                steer_sign_checked: false, trial_settings_reviewed: false}      # 사람이 확인하고 true로 설정
```

STM 튜닝 권장값은 `yaw_max_mdeg` 20000, `yaw_rate_mdeg_s` 20000이며 pitch는 기본값을 유지합니다. 근거는 [`README.md`](README.md)의 "보드 준비"에 있습니다.
